03SDLC 全流程是如何编排的

这套流程不是"几个 skill 的零散集合"，而是把软件开发生命周期（SDLC）的每个阶段都"制度化"地映射到了固定的环节、产物和检查点上。任何一个需求，从进入系统到上线，都走同一条流水线。

先理解：整套机制 = "记忆 → 能力 → 编排"三层

Claude Code 每次启动自动加载这些文件，从而"记得项目约定、拥有领域技能、按流程干活"。读懂三层，就理解了整条流水线的骨架：

层由谁承载干什么
L1 记忆层CLAUDE.md项目大脑：目录结构、真实命令、后端/前端架构约定（分层依赖、响应格式、铁律）、缓存 Key 规范、数据一致性策略、OpenSpec 入口。把"团队规范"写成文件，而不是口头叮嘱——Claude 每次会话先读它，产出天然符合项目约定。
L2 能力层.claude/skills/ + .claude/commands/opsx/可执行技能包：研发工作流（dev/prod/payment 三个 SKILL.md）、规格驱动（/opsx:* 9 个命令 + openspec-* skill）、质量核验（doc-verify）。按需被 Skill 工具加载。
L3 编排层OpenSpec + Hooks + GitHub Actions让交付"有始有终"：OpenSpec 把需求固化成四件套并归档成真理源；Hooks（settings.json → entire）全程会话留痕审计；GitHub Actions 在 PR 合并后推送通知。
技术栈专家 skill（java-springboot、redis-* 等 30+ 个）也属于 L2 能力层，但属源工程团队自有资产（软链接指向 .agents/skills），未随模板提供，按需自备。
SDLC 阶段流水线环节产物质量检查点
① 需求分析brainstorm（可选）→ propose需求文档（docs/brainstorms/）、proposal.md需求充分性判断（A7 两档策略）
② 系统设计propose 生成设计件design.md（How）、specs/*.md（能力规格）设计门禁 doc-verify（8 Agent）
③ 编码实现opsx:apply 逐任务实现代码 + tasks.md（全部打 [x]）编译验证（apply 后立即执行）
④ 测试验证质量门禁 → test-browser / curl审查修复记录、测试证据（截图/录屏）代码门禁 simplify + code-review（闭环 ≤3 轮）
⑤ 交付发布提交前检查 → commit + PRPR（含门禁结果+测试证据）提交前检查（编译/冲突/配置保护）
⑥ 维护演进archive 归档 + specs 同步 + 经验沉淀归档 change、openspec/specs/ 真理源、docs/solutions/ 踩坑库opsx:verify（归档前一致性核验）
编排的核心思想：文档即任务。需求被转成 proposal → design → specs → tasks 四件套，后续每一步（实现、审查、测试、归档）都以这四件套为准绳；specs 归档后成为长期真理源，下一个需求直接继承。整个生命周期是"文档不断细化、又不断沉淀"的闭环。

为什么是"6 阶段 ↔ 流水线步骤"的映射

  • 每一阶段都有"人"的介入点吗？ 只有两处：开头提需求、结尾 review PR。中间全部自动化，靠 skill 递归调度 + 上下文变量（change 名称、改动文件、门禁结果）在步骤间显式传递。
  • 质量内建（Shift-Left）：文档在写代码之前就过 doc-verify 设计门禁；代码在测试之前就过 simplify + code-review——错误发现得越早，修复成本越低。
  • 失败不阻塞：任何门禁 3 轮不过都不中断流程，而是把遗留问题显式写进 PR 描述，让人类 reviewer 知情（Process over Perfection）。

04需求对接：需求怎么进来、会不会确认、怎么不跑偏

需求进入流水线有四种形态，形态决定走哪条路径。本节回答你最关心的三个问题：需求会跟我确认吗？怎么保证最终实现不跑偏？我提供的需求文档要达到什么标准？

第一步：需求形态 → 路径

需求形态走哪条为什么
完整 PRD / 需求文档（含范围、验收标准、多章节）路径 A custom-claude-template-prod-workflow文档足够详实，doc-verify 的 A7 能完整核验覆盖度；涉及现有代码时设计门禁价值最大
口头描述 / 一段话 / 不完整想法路径 B 先 brainstorm 再走路径 Abrainstorm 是唯一交互步骤，把模糊想法澄清成结构化需求文档（docs/brainstorms/）
简单 bug / 单文件小改 / 纯配置路径 C custom-claude-template-dev-workflow不需要门禁，5 步直接跑，省掉 brainstorm 与 doc-verify
拿不准走哪条时：涉及现有代码的中等及以上规模需求 → 路径 A；小改动 → 路径 C。规模判断看改动文件数，改 1-2 个文件通常就是 C。

第二步：需求会跟我确认吗？

核心机制只有一句话：brainstorm 是全程唯一允许与你交互的步骤。从 propose 开始"不中断原则"生效，流水线默认不停下来问你。

场景会确认吗原因
你给了完整 PRD（有范围/验收标准）不确认命中"跳过 brainstorm"→ 直接 propose；改由 doc-verify 的 A7 需求守卫事后逐条核验覆盖度，偏差会被自动抓出
口头一句话 / 模糊想法会确认命中"执行 brainstorm"→ 交互澄清（可能是多轮问答），产出结构化需求文档后再进自动流程
明确 bug / CRUD / 小改动不确认可映射到明确操作，直接跑 5 步流水线，全程无交互
你说"先帮我理清思路 / 分析一下"会确认用户显式要求探索 → 无条件先进 brainstorm
判断口诀——"跳过 brainstorm"：有 PRD/原型图/详细验收标准、可映射明确 CRUD/API、有 Bug 现象+复现步骤、仅配置/文案/样式。反之（描述 <2 句说不清、全新业务领域、多方多系统联动）必须先 brainstorm。
另外 propose 内部还有一个兜底：生成规格文档时若上下文严重不清晰，也会用 AskUserQuestion 问你，但偏好"合理推断继续推进"。

第三步：需求怎么保证不跑偏（ORIGINAL_REQUIREMENT 机制）

核心原则：需求原文永远被原样保存并贯穿全流程，而不是被 AI"转述"或"概括"——转述即失真。机制分三步：

  • ① 原文缓存：流程第一步就把你从"提到需求"到"现在"的所有消息（不做语义过滤）缓存进上下文变量 ORIGINAL_REQUIREMENT；若走了 brainstorm，则更新为 brainstorm 产出的完整需求文档全文（非摘要），并记录文件路径。
  • ② 同一份数据两处消费：propose 构造 args（R1）与 doc-verify 的 A7 需求守卫（R2）读的是同一份原文——"写设计"和"验设计"基于同一事实，不存在 AI 前后两版需求。
  • ③ 超长降级，保护关键章节：args 超过 5000 字时全文降级为核心要点摘要，但 Scope Boundaries 与 Key Decisions 保留完整原文——这两章是防范围蔓延和防决策漂移的命门。
A7 两档策略：需求文本 >50 字或含明确功能点（如带编号列表）→ 完整核验"需求覆盖度 + 可实施性"；文本过简 → 只做可实施性评审，但强制产出"需求简短警告"（P1 级，不阻塞），提醒你需求描述太短、核验已变浅。

第四步：路径 A 完整操作（拿到 PRD 后）

# 假设你已有一份 PRD.md，操作如下：

> 用 /custom-claude-template-prod-workflow 开发<功能名>
> （然后直接粘贴 PRD 全文，或写"需求文档在 docs/plans/PRD-xxx.md"）

① 步骤 1（可选）需求充分 → 跳过 brainstorm，直接进步骤 2
② 步骤 2 propose 读取 PRD，自动构造 args：
     用户需求 +【需求约束】← Scope Boundaries 原文
                +【关键决策】← Key Decisions 原文
                +【成功标准】← Success Criteria 原文
                +【项目约束】← 从 CLAUDE.md 提取 ≤15 行
   （文档 >5000 字时自动降级为核心要点摘要，但保留 Scope/Key Decisions 全文）
   产物：openspec/changes/<name>/{proposal,design,specs,tasks}

③ 步骤 2.5 doc-verify 设计门禁
   - A7 需求守卫：拿 PRD 原文逐条对照 design/specs，输出覆盖矩阵
     （✅已覆盖 / ⚠️部分覆盖 / ❌遗漏 / 🔄扭曲）
   - A1-A6：文档引用的字段/行号/枚举/影响范围 与代码库一致性
   - A8：跨文档一致性（含 CLAUDE.md 约定）

④ 步骤 3-5 实现 + 代码门禁
   opsx:apply 逐任务实现 → 编译验证 → simplify + code-review 闭环（≤3 轮）

⑤ 步骤 6-9 测试 + 交付
   E2E 测试（或纯后端 curl）→ 提交前检查 → archive 归档
   → commit + PR（描述含：设计门禁结果 + 代码门禁结果 + 测试证据）

第五步：需求文档本身要达到什么标准

需求文档的质量直接决定 A7 核验深度。有这三个章节，全流程才能发挥最大价值：

需求文档章节流程里怎么用缺失的后果
Scope Boundaries（包含/排除）注入 propose args 作为【需求约束】；A7 验证文档是否遵守限定词（仅XX/排除XX）范围蔓延，A7 无法做限定词核验
Key Decisions（关键决策）注入 propose args 作为【关键决策】propose 只能自行推断，可能偏离你的真实决策
Success Criteria（成功标准/验收标准）注入 propose args 作为【成功标准】；A7 映射到设计文档A7 退化为"仅可实施性评审"，覆盖度核验失真
拿到文档后第一件事：确认它有没有上面三节。缺的话，要么让 brainstorm 补齐，要么接受 A7 输出"需求简短警告"（不阻塞，但意味着核验变浅）。

路径 B / 路径 C 速查

  • 路径 B（模糊想法）：`/custom-claude-template-prod-workflow 我想做X但还没想清楚` → 步骤 1 brainstorm 交互澄清 → 产出 docs/brainstorms/ 需求文档 → 该文档自动成为 propose 输入（与 PRD 同等对待），随后流程同路径 A。
  • 路径 C（小改动）：直接说"修复XXX"或"开发XXX" → 自动触发 custom-claude-template-dev-workflow → propose → apply → 浏览器测试 → archive → PR。全程无交互。

05验证体系：怎么验证需求、怎么保证实现符合需求、怎么验证功能

"AI 写的东西怎么敢信？"答案不是"信"，而是验证。流水线对每一层转换都设了验证关卡，把"需求 → 设计 → 代码 → 功能"每一步的偏差都拦下来。整个验证体系 = 四层验证（分别回答需求、文档、实现、功能四个问题）+ 一道质量旁路。

四层验证总览

验证什么在哪个环节用什么验证产出
L1 需求被理解对吗（需求 → 设计）步骤 2.5 设计门禁doc-verify 的 A7 需求守卫覆盖矩阵（✅已覆盖/⚠️部分/❌遗漏/🔄扭曲）+ Verdict
L2 文档是真实的吗（设计 → 代码库）步骤 2.5 设计门禁doc-verify 的 A1-A6 + A8一致性发现清单 + 自动修复 + Verdict
L3 代码实现文档了吗（代码 → 设计）步骤 3 之后 / 归档之前编译验证 + opsx:verifyCompleteness / Correctness / Coherence 三维报告
L4 功能真的能用吗（功能 → 需求）步骤 6 端到端测试test-browser（前端）/ curl（后端）功能点通过清单 + 截图/录屏证据
质量旁路：步骤 4-5 的代码门禁（simplify + code-review）验证的不是"需求"，而是"写得好不好"（重复/复杂度/安全/性能）——它保证交付物达标，而 L1-L4 保证交付物符合需求。两件事互相独立。

L1 需求验证：A7 需求守卫 —— "要的是不是这个东西"

  • 输入：ORIGINAL_REQUIREMENT 原文（不是 AI 概括后的摘要）。
  • 做什么：把需求原文逐条对照 design/specs，输出覆盖矩阵：✅ 已覆盖⚠️ 部分覆盖❌ 遗漏🔄 扭曲；同时做可实施性评审（每项是否可实现、依赖是否齐全、边界是否清晰）。
  • 两档策略：需求 >50 字或含明确功能点 → 完整运行；过简 → 仅可实施性 + 强制"需求简短警告"（P1，不阻塞）。
  • 意义：这是全流程唯一直接对照"你的原始需求"的环节，专门抓"要的是 A、文档做成 B"。

L2 文档验证：doc-verify 8 Agent —— "文档是不是 AI 编的"

8 个并行 Agent（sonnet）从不同维度找文档的"幻觉"（文档声称的东西代码里根本不存在）：

Agent核验维度
A1 字段守卫文档写的字段名 / 类型 / 值域 vs 实际 DO/VO/Entity
A2 行号猎手文档引用的 文件名:行号、方法名 是否真实存在
A3 逻辑侦探文档描述的流程 vs 代码实际执行路径
A4 枚举审计枚举值、字典值、状态码是否对得上
A5 影响雷达变更影响范围是否漏了关联模块
A6 边界猎手边界条件 / 异常路径在文档里有没有交代
A7 需求守卫（见 L1）需求覆盖度 + 可实施性
A8 跨文档一致性多份文档（含 CLAUDE.md 约定）之间是否自相矛盾
  • 合并管线：容错解析 JSON → 指纹去重（同一问题被 2+ Agent 命中则标注"多 Agent 共识"提升可信度）→ 分队列（auto-fix / interactive / bugs）→ 按 severity 排序。
  • 修复策略：行号偏移、字段拼写这类简单问题自动修（只改文档、绝不改代码）；业务逻辑偏差这类复杂问题，独立调用时批量问你，工作流模式下记录后继续。
  • 闭环 ≤3 轮：仍有 P0/P1 → 重跑 8 Agent（第 2 轮起附加"已修复内容"做增量核验，省 context）。3 轮仍不过 → 结果记进 PR 描述，不阻塞。

L3 实现验证：编译 + opsx:verify —— "代码真的实现了文档吗"

  • 编译验证：apply 一结束立即跑构建，编译不过先修代码——"在无法编译的代码上做 review 是浪费时间"。失败就地修，最多 3 次。
  • opsx:verify 三维度：
    • Completeness（完整性）：tasks.md 是否全部打 [x]；delta specs 里每条 Requirement 在代码库是否有实现证据。
    • Correctness（正确性）：实现是否偏离需求意图（关键词搜索 + 代码路径分析）；specs 里每条 Scenario 是否被实现、有无测试覆盖。
    • Coherence（一致性）：实现是否遵循 design.md 的关键决策；新代码是否符合项目模式（命名/目录/风格）。
  • 三级问题：CRITICAL（归档前必须修）/ WARNING（应修）/ SUGGESTION（可改）。每条都带具体修复建议与 文件:行 定位，禁止空话"请 review"。
  • 启发式原则：拿不准时降级（SUGGESTION 优先于 WARNING 优先于 CRITICAL），避免误报阻塞交付。

L4 功能验证：端到端测试 —— "功能真的能用吗"

改动类型验证方式证据
前端 / 全栈变更test-browser headed 可视化模式，交互操作逐步验证截图（{分支}_{日期}_NN-描述.png）+ 录屏 .webm，经临时 GitHub Release 嵌入 PR body
纯后端变更curl 探活健康检查 + 核心接口断言HTTP 状态码 + 返回体
  • 测试 URL 推断：按改动文件找消费它的前端路由；动态参数从库里查一条有效记录；推断不了用首页兜底。
  • 失败闭环：关键测试失败 → 就地修复 → 重测，最多 3 次；3 次仍失败记入 PR 描述。
  • 经验沉淀：只要测试失败过（哪怕最终通过），就触发 compound 把"Bug → 根因 → 修复 → 验证"归档到 docs/solutions/，下次不再踩同一个坑。

失败不阻塞：为什么门禁不是"一票否决"（Process over Perfection）

每个验证环节都允许失败、上限 3 轮，3 轮后把遗留问题显式写进 PR 描述，由人类 reviewer 知情终审。理由：流水线中途反复重试会烧掉大量 context，且 AI 自我修复存在边际递减；把问题透明化交付给人类把关，比假装"全绿"更诚实、更安全。PR 描述承载的正是四层验证的完整证据链。

entire hooks 详解：entire hooks claude-code post-task 这句话到底在干嘛？

entire 是开源会话遥测 CLI（github.com/entireio/cli），把"AI 是怎么把代码写出来的"全程留痕并关联 git 提交：保留每轮 prompt、改动的文件、工具调用、token 用量，支持任意 checkpoint 续接。它不是 Claude Code 自带的，而是通过 settings.json 的 hooks 挂进来。以 entire hooks claude-code post-task 为例拆开看：

  • entire —— 调用该 CLI（需先安装）
  • hooks claude-code —— "我要处理 Claude Code 的 hook 事件"，第二个参数是 agent 名
  • post-task —— 具体事件名：子 Agent（Agent 工具）执行完毕后触发

它出现在 PostToolUse 分组下、matcher 为 Agent：每当 Claude 启动一个子 Agent 且其返回结果，Claude Code 就把这次工具调用的 JSON 上下文通过 stdin 交给这条命令，entire 据此打一个"子任务结束"的 checkpoint，记录改动的文件、耗时与 token 用量。完整 hook 矩阵（matcher 已按当前 Claude Code 更新——Task 工具已改名 Agent，TodoWrite 已被 TaskCreate|TaskUpdate 取代，旧 matcher 在新版上会静默失效）：

settings.json 分组matcherentire 事件触发时机
SessionStart（全部）session-start会话启动，开始累计当前 session
UserPromptSubmit（全部）user-prompt-submit每条用户消息提交，记录完整需求原文
PreToolUseAgentpre-task子 Agent 启动前
PostToolUseAgentpost-task子 Agent 结束后
PostToolUseTaskCreate|TaskUpdatepost-todo任务清单更新后，记录进度

数据落在 .entire/ 目录——这就是纯净版 settings.json 里 deny Read(./.entire/metadata/**) 的原因：审计数据不允许 AI 自己读取改写。

09.02agent-browser 详解：浏览器测试工具

一句话：让 AI agent 能像真人一样操作真实浏览器做端到端测试（Vercel Labs 出品、Playwright 驱动的工具）。流水线里的 test-browser 步骤就靠它完成"前端功能验证 + 截图录屏留证"。

  • 起什么作用：开真实 Chromium（无头或 --headed 可视），agent 驱动它打开页面、点击、填表、翻页，实测功能是否可用——而非只读代码"猜"行为。测试结果（截图/录屏）存进 docs/solutions 形成验收证据链，也是 PR 的可视化说明。
  • 怎么调用（两种方式，二选一或并用）：

    ① 命令行直接驱动——流水线（test-browser 步骤）的默认方式，agent 直接在 Shell 里执行它：

    agent-browser --headed open "http://localhost:3001"          # 打开被测页面
agent-browser --headed screenshot "…/01-initial-state.png"   # 操作前留证
agent-browser --headed click "text=加入购物车"                  # 执行真实点击
agent-browser --headed record start "…/recording.webm"        # 全程录屏
agent-browser --headed record stop

    ② MCP Server 暴露成工具——agent-browser 内置 agent-browser mcp 命令，启动一个 stdio 的 MCP Server，把 open/click/snapshot 等封装成标准 MCP 工具，任何支持 MCP 的客户端都能在对话里直接"调用工具"（常见于 Codex/Kiro/Cursor/Cline 等非 Claude Code 工具）。默认暴露 core 工具集（导航/交互/截图/读取），可用 --tools all 开全部。

  • 什么时候缺它不可：前端/全栈变更必须过浏览器实测；仅改后端时流水线会自动降级为 curl API 验证，不强制依赖它。

09.03agent-browser MCP 接入配置

流水线已在 Claude Code 里走命令行方式，无需配置。若你的团队也用 Codex / Kiro / Cursor / Cline 等工具做浏览器测试，按各自约定把 MCP Server 注册进去即可（共用同一套命令）：

客户端配置文件配置示例
Claude Code.claude/mcp.json（或 claude mcp add）{ "mcpServers": { "agent-browser": { "command": "agent-browser", "args": ["mcp"] } } }
Codex（OpenAI）.codex/config.toml（或 codex mcp add agent-browser -- agent-browser mcp）[mcp_servers.agent-browser]\ncommand = "agent-browser"\nargs = ["mcp"]
Kiro.kiro/settings/mcp.json{ "mcpServers": { "agent-browser": { "command": "agent-browser", "args": ["mcp"] } } }
Cursor.cursor/mcp.json同 Claude Code 的 JSON（mcpServers 键）
Cline（VSCode 插件）cline_mcp_settings.json{ "mcpServers": { "agent-browser": { "type": "stdio", "command": "agent-browser", "args": ["mcp"] } } }

要点：所有客户端注册的都是同一套 command: "agent-browser", args: ["mcp"]，只是配置文件位置/格式不同。想开全部工具把 args 改为 ["mcp", "--tools", "all"]。任何 MCP 客户端（Claude Desktop、Gemini CLI、VS Code 等）同理，按自己的 MCP 配置入口粘贴即可。

09.04OS 级沙箱兜底：完全放权也不怕 rm -rf

解决什么问题：agent 频繁弹确认打破自动化 vs 全部授权（--dangerously-skip-permissions）太危险——两者的矛盾。业界共识是权限放给 agent，安全交给 OS：确认环节从"事中"移到"事前约束 + 内核兜底"。

  • 原理（两层隔离）：权限规则（--dangerously-skip-permissions 只绕过这层，决定"是否先问你"）与 OS 沙箱（内核强制，决定"命令实际能不能碰"，谁也绕不过）是两层。沙箱开着时，即使 agent 毫无犹豫执行 rm -rf /，内核也会拒绝它删工作目录以外的文件。
  • Claude Code 内建：会话里输 /sandbox 开启，macOS 用 Apple Seatbelt（内核级强制访问控制，Chromium/VS Code 同款），零安装零依赖；Linux/WSL2 用 bubblewrap。开启后沙箱内 Bash 命令自动放行（auto-allow），确认弹窗实测下降 84%。
  • Codex / Kiro：Codex 默认就带 OS 沙箱（sandbox-first），codex exec --sandbox workspace-write --ask-for-approval never；Kiro 基于 Claude Code 内核，同样支持 /sandbox。

开箱即用配置（.claude/settings.sandbox.json.example）：

# 复制为 settings.json（或 settings.local.json，仅本项目生效）
cp .claude/settings.sandbox.json.example .claude/settings.json
# 效果：沙箱内命令全自动不打断；写操作锁死在工作目录；
#      ~/.ssh、~/.aws 等敏感路径禁止读写；网络只通白名单域名

配置要点：

  • autoAllowBashIfSandboxed: true — 沙箱内命令免确认（完全放权的来源）
  • allowUnsandboxedCommands: false — 关掉逃生门：任何命令不允许跑出沙箱，杜绝"沙箱外裸奔"
  • network.allowedDomains — Bash 命令能访问的域名白名单（npm/github/maven 等），其余请求内核直接拒绝；本地 dev server 需 allowLocalBinding: true
  • permissions.deny — 兜底敏感路径保护（SSH 私钥、云凭据、shell 配置），Read/Edit 双重封死

底线：--dangerously-skip-permissions 只应在隔离环境（CI 容器 / dev container / VM）里与沙箱配合使用；本地开发用 /sandbox + 上面这份配置即可实现"完全放权 + 电脑安全"。

09.05mac 上的隔离方案选型：VM / Docker / 云端怎么选

根本差异：mac 上没有原生容器支持——所有容器方案都必须先起一个 Linux VM，容器再跑在 VM 里。这决定了各种方案在 mac 上的优劣分布：

方案mac 上的实现隔离强度主要劣势
Docker Desktop先起 Linux VM 再跑容器中（共享内核）系统调用穿透 VM，IO 比 Linux 原生慢 30-50%；文件同步跨 VM 边界（inotify 失效，前端 HMR 常不触发）；VM 常驻 2-4GB 内存；node_modules 不能跨边界挂载
OrbStack轻量 Linux VM + 容器中比 Docker Desktop 快，但文件映射仍是跨 VM 边界，同样的同步损耗
Podman同样要起 VM中mac 上工具链不成熟、周边生态少
UTM / QEMU完整虚拟机高（整机隔离）无 GPU 直通，前端构建/浏览器测试慢；共享文件夹性能差，git 跨 VM 易出权限/换行符问题；VM 常驻 4-8GB 内存；启动慢，交互割裂
Parallels / VMware完整虚拟机高收费（Parallels 按年订阅）；同样吃内存；自动化配置比开源方案繁琐
Vercel Sandbox / Claude Code on the web云端 microVM / 托管 VM最高（物理隔离，本地零污染）依赖网络，断网即中断；按 token/时长计费，高频不便宜；代码上传第三方，机密项目不适合；本地调试（dev server 回连）复杂
/sandbox + Seatbelt（Claude Code 内建）内核级，无需 VM中（进程级）默认只拦 Bash 及子进程，不拦 MCP/hooks（需 @anthropic-ai/sandbox-runtime 才能全进程包裹）；macOS 限定（Linux 用 bubblewrap）

针对本项目场景（mac + 交互式本地开发 + 无人值守）的最务实组合：

  • 本地日常（人在）：/sandbox + Seatbelt——零开销，白名单外一切被内核拦截，确认弹窗大幅减少，写操作锁死工作目录。
  • 无人值守（CI）：GitHub Actions 的 ubuntu runner——runner 本来就是一次性隔离环境，比在本地 mac 上再套 Docker/VM 省心得多，且零额外成本。

为什么不建议在 mac 上把 agent 关进 Docker/VM：为"隔离"付出 30-50% IO 损耗 + 文件同步坑 + 常驻内存，而 CI runner 天然就是隔离环境。mac 上的 Docker 适合跑基础设施中间件（本模板的 PostgreSQL/Redis/ES/MinIO 就是这么用的），而不是把 agent 关进去。完整对比见上方表格。

09.06skills-lock.json：skill 锁文件怎么产生、有什么用

一句话：它是 skill 生态里的 package-lock.json——记录项目从 GitHub 装了哪些 skill、各自来源与内容哈希，保证"换机器 / 新同事 / CI"能装回完全一致的版本。

它从哪来：由 Vercel Labs 的 npx skills CLI 自动生成（不是手工写的）。用该工具从 GitHub 安装 skill 时，会写入/更新项目根目录的 skills-lock.json（全局安装则写 ~/.agents/.skill-lock.json）：

# ① 安装 skill（拉取 GitHub 仓库，自动写入 skills-lock.json）
npx skills add ant-design/antd-skill

# ② 检查更新（对比本地内容哈希 vs 上游，检测 SKILL.md 被改）
npx skills check

# ③ 按锁文件精确恢复（等价 npm ci——换机器/CI 只跑这一步）
npx skills experimental_install

锁文件内容示例（每个 skill 一条，记录来源 + 内容哈希）：

{ "version": 1, "skills": {
    "java-springboot": { "source": "github/awesome-copilot", "sourceType": "github", "computedHash": "f1b9c6b1…" },
    "redis-best-practices": { "source": "mindrally/skills", "sourceType": "github", "computedHash": "c362f644…" }
} }

有什么用：

  • 可复现——experimental_install 能装回一模一样的内容，团队协作和 CI 不再靠"口口相传怎么装的"。
  • 防篡改 / 可审计——computedHash 是全部文件的内容哈希，上游 skill 被动过（哪怕改一行）就能查出来；PR 里可直接 diff skill 变更。
  • 明确依赖——列出项目依赖了哪些第三方指令包、来自哪个仓库，供供应链审查。
注意区分：Claude Code 官方 skill 系统（.claude/skills/SKILL.md）本身不需要锁文件——只有用 npx skills 这类工具管理第三方 skill 时才产生它。手动复制进 .claude/skills/ 的 skill（如本模板的 doc-verify、openspec-*）不会出现在 lock 里。一致性要求：一旦采用 npx skills 管理，安装/更新就都走它（避免手工改 lock 或绕过它装 skill，否则 lock 与实际安装对不上、可复现性即失效）；skills-lock.json 建议提交 git 与团队共享。
