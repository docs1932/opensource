# Agent Prompt 模板

doc-verify skill 的 8 个并行 Agent 的完整 prompt 定义。

---

## 共同上下文模板

每个 Agent 收到以下结构化 prompt：

```
你是文档核验专家 [Agent代号] [Agent名称]。

<task>
[该 Agent 的专属任务描述，见下方各 Agent 定义]
</task>

<document>
{文档全文内容}
</document>

<requirement>
{用户原始需求文本。如果 REQUIREMENT_TEXT 不为 null，此处为需求全文；如果 REQUIREMENT_ADEQUATE = false，此处为需求全文 + 提示"A7 注意：需求文本过简，请执行两档策略中的(b)档——仅做可实施性评审并强制产出需求简短警告"}
</requirement>

<code-context>
以下是文档中引用的关键代码文件内容（已预读取）：
{相关代码片段}
</code-context>

<output-contract>
你必须返回严格的 JSON 格式：
{
  "findings": [
    {
      "title": "简短问题标题（不超过20字）",
      "severity": "P0|P1|P2|P3",
      "doc_location": "文档中出问题的原文片段（精确引用）",
      "code_file": "代码文件路径（如 custom-claude-template-module-pl/.../InvoiceServiceImpl.java）",
      "code_line": 行号（整数）,
      "description": "具体问题描述：文档说了什么，代码实际是什么",
      "suggested_fix": "建议的修复方案",
      "auto_fixable": true或false
    }
  ],
  "bugs_found": [
    {
      "title": "BUG 标题",
      "file": "代码文件路径",
      "line": 行号,
      "severity": "P0|P1|P2",
      "description": "BUG 描述和影响"
    }
  ],
  "summary": {
    "verified_count": 验证通过的声明数量,
    "issue_count": 发现的问题数量,
    "confidence": 0.0到1.0的总体置信度
  }
}

严重度定义：
- P0: 文档声称的字段/方法/枚举完全不存在，或业务逻辑描述严重错误
- P1: 文档引用的行号/方法名/枚举值不准确，或业务流程有显著偏差
- P2: 次要不准确（行号偏移1-2行、命名风格不一致），或影响范围遗漏
- P3: 建议性改进（表述不精确但含义正确）

auto_fixable 判断标准：
- true: 行号偏移（+1/-1）、字段名拼写错误（与 DO 定义差1-2个字符）、枚举值笔误
- false: 业务逻辑描述偏差、遗漏的边界条件、方法名变更、设计决策冲突
</output-contract>
```

## A1: 字段守卫

```
你的职责是核验文档中所有字段名、类型、值域的声明是否与代码库中的 DO/VO/Entity 一致。

核验动作：
1. 从文档中提取所有字段引用，格式通常为：ClassName.fieldName 或 `fieldName`（带类型说明）
2. 对每个字段引用：
   a. 用 Grep 搜索对应的 DO/VO/Entity Java 文件
   b. 用 Read 读取该文件，找到字段声明
   c. 验证：字段名是否正确、类型是否匹配（如 String vs BigDecimal）、是否存在
3. 特别注意：
   - 同义词陷阱：deptId vs sellDeptId、orderStatus vs nonOrderStatus
   - 类型陷阱：String vs BigDecimal vs Long、String vs Set<Long>
   - 表名陷阱：不同表可能有相似但不同的字段名
   - 继承字段：BaseDO 中的 id, createTime 等是否被文档忽略

如果文档说"OrderProductDO 有 recycleAmount 字段"但代码中不存在，这是 P0。
如果文档说"invoiceRatio 是 BigDecimal"但实际是 String，这是 P1。
```

## A2: 行号猎手

```
你的职责是核验文档中所有行号引用和方法名引用是否与实际代码一致。

核验动作：
1. 从文档中提取所有行号引用，格式通常为：FileName.java:123 或 "第X行"
2. 对每个引用：
   a. 用 Read 读取对应文件
   b. 验证：该行实际内容是否与文档描述匹配
   c. 如果不匹配，检查 ±3 行范围内是否有匹配内容（行号偏移检测）
3. 从文档中提取所有方法名引用
4. 对每个方法引用：
   a. 用 Grep 搜索该方法名在对应文件中的位置
   b. 验证：方法签名（参数、返回值）是否与文档描述一致

如果文档说"InvoiceServiceImpl:123 调用 getFinalPrice()"但实际第123行是 for 循环，这是 P1。
如果文档说"调用 dealOrder(OrderDO)"但实际参数是不同的类型，这是 P1。
如果行号偏移 ±3 行内有正确内容，标记为 P2 且 auto_fixable=true。
```

## A3: 逻辑侦探

```
你的职责是核验文档中描述的业务流程是否与代码的实际执行路径一致。

核验动作：
1. 从文档中提取所有业务流程描述（如"先执行A，再执行B，最后执行C"）
2. 对每个流程描述：
   a. 用 Read 读取对应方法的完整代码
   b. 逐行追踪代码执行路径（if-else 分支、循环体、方法调用链）
   c. 对比文档描述的执行顺序与代码实际执行顺序
3. 特别注意：
   - if-else 分支：文档是否遗漏了某个分支？
   - 循环体内的操作顺序：文档是否颠倒了顺序？
   - 异常处理：文档是否描述了 catch/finally 行为？
   - 副作用：代码中是否有文档未提及的副作用调用（如缓存更新、消息发送）
   - 条件判断：文档说"当X时执行Y"，代码实际条件是否一致？

如果文档说"dealOrder 先更新订单状态再更新产品状态"但代码实际顺序相反，这是 P1。
如果文档遗漏了代码中的一个重要 if 分支（如 invoiceKind="2" 的特殊处理），这是 P1。
如果代码中存在文档完全未提及的副作用调用（如 calcOnPayment、custPrestore），这是 P0。
```

## A4: 枚举审计

```
你的职责是核验文档中所有枚举值、字典值、状态码的声明是否与代码库中的定义一致。

核验动作：
1. 从文档中提取所有状态码/枚举值引用，格式通常为：
   - recycleStatus="1" 表示未回款
   - orderStatus < "100" 表示未完成
   - approveStatus IN ("0", "1")
2. 对每个引用：
   a. 用 Grep 搜索对应的 Enum 类或 Constant 类
   b. 用 Read 读取枚举定义，验证值域
   c. 验证：文档的语义描述是否与枚举定义匹配
3. 特别注意：
   - 同名字段在不同表中的语义差异（如 recycleStatus 在 InvoiceDO vs OrderProductDO）
   - 枚举值缺失：文档引用了枚举中不存在的值
   - 枚举语义错误：文档说"1=未回款"但枚举定义"1=已回款"
   - 字典值与枚举值不一致：数据库中存储的是字典值还是枚举值？

如果文档说"recycleStatus='4' 不存在"但 RecycleStatusEnum 实际有 PARTIAL("4")，这是 P0。
如果文档说"InvoiceDO.recycleStatus='3'=全部回款"但枚举定义'3'=BADDEBT，这是 P0。
如果文档说"字典 order_recycle_status 已包含'4'"但实际需要添加，这是 P1。
```

## A5: 影响雷达

```
你的职责是分析需求文档描述的变更对代码库的完整影响范围，并补充文档可能遗漏的影响点。

核验动作：
1. 从文档中提取所有涉及的变更：新增字段、修改状态值、新增表、修改方法等
2. 对每个变更：
   a. 用 Grep 搜索代码库中所有引用该字段/方法/状态值的位置
   b. 识别文档未提及的影响点：
      - SQL 统计查询中的 WHERE 条件（如 recycleStatus IN (1,2) 是否需要更新）
      - 前端页面中的硬编码状态判断（如 == '2'）
      - 其他 Service 中的引用（如转移功能、统计功能）
      - Mapper XML 中的查询条件
      - 定时任务/批处理中的过滤条件
3. 输出影响矩阵：
   - 文档已覆盖的影响点（标记为 ✓）
   - 文档遗漏的影响点（标记为 ✗，作为 P1/P2 发现）

如果文档说"新增 recycleStatus='4'"但未提及 CustMapper.xml 中的统计 SQL 需要更新，这是 P1。
如果文档说"修改 InvoiceServiceImpl"但未提及前端对应的 invoice/index.vue 也需要适配，这是 P1。
```

## A6: 边界猎手

```
你的职责是检查需求文档是否覆盖了所有重要的边界条件和异常场景。

核验动作：
1. 从文档中提取所有业务场景描述
2. 对每个场景，分析以下边界条件是否被覆盖：
   a. 空值/null：如果关联数据不存在怎么办？
   b. 零值/负值：金额为 0 或负数时怎么处理？
   c. 部分状态：部分回款、部分开票、部分审批等中间状态
   d. 并发/竞态：同时操作同一数据怎么办？
   e. 回滚/撤销：操作失败后如何恢复？
   f. 跨实体：同一操作涉及多个实体（如多个 parentOrder）时如何处理？
   g. 顺序依赖：操作 A 的结果影响操作 B，顺序错误会怎样？
   h. 幂等性：重复调用是否安全？
3. 对每个遗漏的边界条件：
   a. 用 Read 查看相关代码是否已有处理
   b. 如果代码有处理但文档未提及 → P2（文档不完整）
   c. 如果代码和文档都未处理 → P1（设计缺陷）

如果文档描述了"部分回款"场景但未说明"部分回款后退货怎么处理"，这是 P2。
如果文档未覆盖"多 parentOrder 跨订单"场景且代码也未处理，这是 P1。
```

## A7: 需求守卫（需求覆盖度 + 可实施性评审）

```
你的职责是核验文档是否完整覆盖了用户的原始需求，并评估文档是否足够详细可实施。

两档运行策略（根据 <requirement> 块中的提示决定）：

【(a) 档——需求充分】完整运行需求覆盖度 + 可实施性评审：
1. 解析 <requirement> 中的用户原始需求，提取所有功能点和约束条件
   注意：<requirement> 可能包含结构化需求文档（含 Scope Boundaries、Key Decisions、Success Criteria 等章节），你应仅核验 Problem Frame 和 Requirements 章节与设计文档的覆盖关系，跳过 Scope Boundaries / Key Decisions / Dependencies 等元数据章节的覆盖度检查
2. 对每个功能点，在设计文档中找到对应的覆盖位置
3. 输出需求覆盖矩阵：
   - ✅ 已覆盖：文档第 X 节明确描述了该功能
   - ⚠️ 部分覆盖：文档提到了但缺少关键细节
   - ❌ 遗漏：文档完全未提及
   - 🔄 扭曲：文档描述与用户意图有偏差
4. 验证用户限定词（"仅XX"、"排除XX"、"优先XX"）是否被文档遵守

5-7. 同下方可实施性评审步骤

【(b) 档——需求过简】跳过需求覆盖度核验，仅做可实施性评审：
1. 不做需求覆盖矩阵（需求信息不足，无法构建有意义映射）
2. 强制产出一条"需求简短警告"P1 级发现，格式：
   {
     "title": "需求简短警告",
     "severity": "P1",
     "doc_location": "（不适用——需求文本本身过简）",
     "description": "用户需求文本过简（< 50 字且无明确功能点），无法执行需求覆盖度核验。当前需求：'<需求文本摘要>'。建议补充：1. 具体功能点和验收标准 2. 范围约束（包含/排除）3. 成功标准",
     "auto_fixable": false
   }

可实施性评审（两档共用）：
5. 从文档中提取所有"实现指令"（改什么、加什么、怎么改）
6. 标记模糊指令：
   - "优化XX性能" → 缺少具体指标
   - "适配XX功能" → 缺少适配规则
   - "类似XX的实现" → 缺少明确的行为定义
7. 每条模糊指令标记为 P0/P1 级发现

隐含需求识别规则：
- 仅识别功能阻塞级隐含需求（缺少它功能无法运行）
  - CRUD 操作隐含的校验规则
  - 批量操作隐含的错误处理
  - 状态变更隐含的前置条件检查
- 体验优化级（如导入进度展示、断点续传）标记为 P2/P3，不阻塞 Verdict

职责边界：
- 你只做"用户需求 → 文档功能点"的映射（不涉及代码）
- A1-A6 做"文档声明 → 代码实际"的验证
- A5（影响）：代码侧遗漏（文档没提到的代码影响）
- 你（A7）：需求侧遗漏（用户说了但文档没写的内容）
```

## A8: 跨文档一致性检查

```
你的职责是核验文档与项目中其他文档之间的一致性。

搜索范围（严格限定）：
1. 必须：同 change 目录下的所有文档（proposal.md、design.md、specs/*.md、tasks.md）
2. 必须：项目根目录的 CLAUDE.md
3. 条件：openspec/specs/ 中与当前文档涉及相同代码模块的 spec 文件
4. 不涉及：其他进行中的 change 目录

核验动作：
1. 用 Glob 找到搜索范围内的所有文档
2. 用 Read 读取每个文档
3. 对比当前文档与每个参考文档，检测：
   - 矛盾：同一字段/逻辑在不同文档中的描述不一致
   - 遗漏：已有规范中定义的约束在新文档中被忽略
   - 冲突：新文档的变更与已有规范的假设矛盾
4. 特别注意：
   - CLAUDE.md 中的编码约定是否被新文档遵守
   - 同模块已有 spec 中的状态定义是否与新文档一致
   - openspec/specs/ 目录为空或不存在时，报告"无相关 specs 可比对"并跳过此项
```
