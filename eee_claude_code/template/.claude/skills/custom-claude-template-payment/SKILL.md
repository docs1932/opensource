# 支付渠道接入工作流

用户提供支付渠道信息和开放平台文档后，按以下步骤顺序执行，完成新支付渠道的完整接入。

---

## 前置确认清单

开始实现前，向用户确认以下信息（缺一不可）：

| 序号 | 信息项 | 示例 |
|------|--------|------|
| 1 | 渠道名称 | 支付宝（开放平台） |
| 2 | 商户身份标识 | app_id（应用 ID）+ 关联的商户号 PID |
| 3 | 应用公钥 / 应用私钥 | 平台用公钥验签，我方用私钥签名（RSA2） |
| 4 | 平台公钥 / 平台证书 | 用于验签异步通知与平台返回 |
| 5 | 支付产品类型 | 电脑网站支付 / APP 支付 / 手机网站支付 / 当面付 |
| 6 | 签名与编码规则 | RSA2 + SHA256，UTF-8，时间戳格式 |
| 7 | 异步通知地址（回调 URL） | https://api.example.com/api/v1/pay/notify/alipay |
| 8 | 同步跳转地址（仅网页类产品） | https://www.example.com/order/result |
| 9 | 金额处理规则（精度/币种） | 金额×100 存整分，CNY 两位小数 |
| 10 | 对账/退款接口可用性 | 是否开通退款、对账单下载、关单接口 |

**如果用户没有提供完整信息，主动追问缺失项，不要猜测。**

---

## 步骤 1：确认渠道资质与账号

在开放平台完成以下事项，全部具备后才进入开发：

1. 完成企业认证，创建应用并提交审核，获取 `app_id`
2. 生成/配置密钥对：我方应用公钥上传平台，平台公钥下载保存
3. 确认该应用已开通目标支付产品（下单/退款/对账权限）
4. 开通沙箱环境或联调环境，拿到测试账号与测试密钥
5. 把正式与沙箱的密钥分开存放，禁止硬编码进仓库

**未通过审核或权限未开通时，先停下与用户确认，不要用 mock 替代真实联调。**

---

## 步骤 2：数据库配置与迁移

新增渠道属于"新增一条配置"，不要改动既有表结构。按以下约定操作：

1. 在 `scripts/db/` 下创建迁移脚本，文件名取当前最大版本号 +1
2. 往 `payment_channel_config` 表插入一条渠道配置：
   - 渠道编码（如 `ALIPAY_WAP`）、渠道名称、app_id、密钥引用（存 KeyVault 或环境变量，不落库明文）
   - 下单/通知/查询/退款的接口地址（沙箱与正式分开）
   - 支付产品类型、回调 URL、币种、是否启用
3. 若需记录支付流水，确认 `payment_transaction` 表字段覆盖：商户订单号、渠道交易号、金额、状态、扩展字段（存异步通知原始报文用于对账）
4. 迁移脚本执行方式：`psql` 执行 `scripts/db/V{N}__*.sql`，并核对影响行数

**密钥类配置一律放配置中心/环境变量，禁止写进 SQL 与仓库。**

---

## 步骤 3：签名与验签封装

在所有接口调用之前，先把签名/验签做成一个独立工具类（复用，不随渠道变化）：

1. **请求签名**：按渠道规范拼接待签名串（字段按字典序，排除空值与签名本身），用应用私钥做 RSA2 签名
2. **响应验签**：收到平台响应后，用平台公钥验签，验签失败视为无效响应
3. **异步通知验签**：收到回调时同样验签，并校验"业务参数 + 签名"完整性
4. 统一封装点：只允许一处实现签名逻辑，其余模块调用它，避免各接口各写一遍

**签名算法必须与渠道文档逐字对齐（参数拼接、编码、空值处理），是联调时最容易翻车的地方。**

---

## 步骤 4：统一下单

实现下单入口（创建支付单并返回跳转参数/支付二维码）：

1. 校验订单：订单存在、状态可支付、金额与商品一致
2. 幂等：同一商户订单号重复调用时返回同一笔支付参数，不重复创建渠道交易
3. 组装请求参数（金额/商品标题/商户订单号/异步通知地址/同步跳转地址）
4. 调用渠道下单接口，拿到支付跳转表单或二维码内容
5. 落库：把商户订单号、渠道交易号、下单状态写入 `payment_transaction`
6. 返回给前端：网页类返回表单/跳转 URL，当面付返回二维码内容

**商户订单号要求全局唯一且可幂等重试，推荐"业务单号 + 渠道后缀"的生成规则。**

---

## 步骤 5：异步通知（回调）处理

回调是支付结果流转的核心，处理顺序固定：

1. 收到 POST 通知 → 先验签，验签失败直接返回失败响应（不处理业务）
2. 查库核对：商户订单号对应订单存在，且当前状态未终态（防重复通知）
3. 按通知中的交易状态更新订单与流水状态（支付成功 → 标记已支付、记录渠道交易号）
4. 处理完业务后**立即**返回渠道要求的成功响应体（如 `success`），让渠道停止重推
5. 记录原始通知报文到扩展字段，供后续对账追溯

**回调必须幂等：渠道会重推多次，重复通知不得导致重复发货/重复记账。**

---

## 步骤 6：主动查单

用于补偿异步通知丢失的场景，提供查询能力：

1. 查询接口：按商户订单号或渠道交易号，向渠道发起交易查询
2. 状态映射：渠道返回的支付状态 → 系统订单状态
3. 兜底对账：订单长时间未收到回调时，定时触发主动查询并推进状态
4. 查询结果同样要验签

**查单与回调双通道：通知为主、查单兜底，两者结果不一致时以查单为准并记录差异。**

---

## 步骤 7：退款流程

如果渠道开通了退款权限，实现退款：

1. 退款申请：按商户退款单号、原交易号、退款金额发起
2. 部分退款：金额校验（退款累计金额不超过原订单实付）
3. 幂等：同一退款单号重复提交返回同一结果
4. 退款结果：同步返回则直接更新；异步通知则复用回调链路处理
5. 落库：退款流水单独记录，与支付流水关联

**退款是资金操作，金额校验必须用整分整数运算，禁止浮点比较。**

---

## 步骤 8：定时任务（关单与对账）

接入定时任务处理边界场景：

1. **关单**：超时未支付的订单调用渠道关单接口，避免长期占用支付入口
2. **主动查单补偿**：定期扫描"已下单未回调"的流水，调用查询接口推进状态
3. **对账**（如渠道提供）：下载渠道对账单，与本地流水比对，标记差异单
4. 定时任务按渠道配置开关控制，避免给未接入的渠道空跑

**定时任务是流水线骨架复用点：只注册渠道编码维度，不重复造调度器。**

---

## 步骤 9：验证

### 9.1 编译

```bash
cd backend && mvn clean compile
```

### 9.2 沙箱/联调环境验证支付闭环

1. 用沙箱测试账号发起一笔小额支付（如 0.01 元），走完"下单 → 支付 → 回调 → 状态更新"
2. 验证回调能正常收到达成，且重复通知不重复处理
3. 验证查单兜底：关闭回调模拟通知丢失，确认定时任务能主动把订单状态推进
4. 验证退款：对已支付订单发起退款，确认金额与状态正确
5. 核对支付流水表：订单号、金额、状态、扩展字段完整

### 9.3 正式环境冒烟（灰度）

1. 生产配置开启前，先小额真实支付验证一次全链路
2. 确认回调地址在正式环境可达（公网、HTTPS、防火墙放行）

## 注意事项

### 已踩过的坑

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| 验签一直失败 | 签名串拼接未按字典序 / 空值排除不一致 | 严格按渠道文档拼串，与官方 SDK 的签名样例逐字节比对 |
| 回调重复触发导致重复发货 | 未做幂等处理 | 回调按"通知 ID + 商户订单号"去重，更新时校验状态未终态 |
| 金额丢失精度 | 用浮点存金额 | 金额统一存整分（Long），运算用整数，展示时才转小数 |
| 商户订单号重复 | 下单逻辑重试未做幂等 | 同一单号重复下单直接返回首次创建的支付参数 |
| 沙箱回调到不了 | 沙箱环境未配置公网回调地址 | 用内网穿透/临时公网地址联调，确认后再切正式 |
| 通知报文解析失败 | 渠道变更了字段或编码 | 记录原始报文，用渠道最新文档核对字段名 |
| 退款金额超限 | 未校验累计已退金额 | 退款前校验已退累计 + 本次 ≤ 实付金额 |
| 密钥泄漏到仓库 | 配置直接硬编码 | 密钥走 KeyVault/环境变量，仓库内只留引用，加 gitignore |

### 架构原则

1. **通过统一支付 Service 操作数据** — 下单/回调/退款都走统一入口，不散落在各 Controller
2. **签名验签单一封装** — 全项目只有一处签名实现，渠道差异通过策略注入
3. **渠道编码隔离** — 每个渠道独立配置（如 ALIPAY_WAP、WX_NATIVE），互不干扰
4. **金额整分运算** — 任何金额计算都用整数分，禁止 float/double
5. **回调幂等优先** — 宁可重复通知也不可重复入账，状态机单向推进

### 现有可复用设施

接入新支付渠道时，以下部分**已存在且通用**，不需要重写：

- `payment_channel_config` / `payment_transaction` 表结构 — 通用配置与流水
- 签名验签工具类 — 复用，渠道间仅差异在参数拼装
- 统一下单 / 回调 / 退款入口 — 按渠道配置路由
- 定时任务框架（关单 / 查单 / 对账）— 只注册渠道编码
- 幂等与状态机工具 — 防重复处理

**每个新渠道只需要：**
1. 一条渠道配置（SQL）
2. 渠道特定的请求参数组装与响应解析（与签名工具配合）
3. 渠道特定的状态映射与回调处理规则
